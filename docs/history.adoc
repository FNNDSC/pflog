= pflog: history
:toc:

== Abstract

pflog began in 2023 as a client for pftel, a telemetry server FNNDSC ran to collect timing events from ChRIS plugins, and its one lasting idea was a decorator that timed a plugin's `main` and posted the seconds. Version 2.0, in October 2026, keeps the decorator and removes the server: the span is a record of the same shape as hostlib's record of a process, written on standard error as one line of JSON, and the question of where such lines are collected is left to whatever already collects a program's output.

== 2023: a client for pftel

pftel was a FastAPI service with a path-shaped API, `/api/v1/<object>/<collection>/<event>`, that stored whatever JSON a client posted. Inside, the store was a `C_stree` from pfmisc, a path-addressed in-memory tree held in a pfstate singleton and mirrored to disk under `/home/dicom/telemetry`, a design its own source described as historical and to be discouraged. pflog 1.x was the Python side: a `Pflog` class wrapping the generated `pftel-client`, a `pfprint` convenience that posted one message, a `pflog` command for doing the same from a shell, and `tel_logTime`, a decorator that took two `pftag` timestamps around a function, printed the difference, and, when a `--pftelDB` URL was found among the function's arguments, rewrote the URL's last element to the decorator's event name and posted the seconds there as `execTime`.

pl-shexec and the LLD workflow plugins wore the decorator, and pftel on the MOC held a per-stage breakdown of each workflow that the platform's own view of plugin instances, scheduled to finished, could not give, since that span included image pull, input copy, queue wait and output copy around the computation. That was the idea worth keeping. What came with it was heavier than the idea: the decorator depended on pftag for its timestamps, on pudb and loguru by habit, on pftel-client for the post and on pfstate through the server; it posted the time whatever `main` returned, so a failed run and a successful one looked alike; a failed post inside a compute pod raised through to the plugin; and the only consumer of the data was a CSV endpoint on the server. The package stopped at 1.2.26 in March 2023 with three known crashes.

== 2026: the record without the server

The pf* revitalization of October 2026 rebuilt pftree, pfdo, pftag and pfdo_run in order and created hostlib as the one home for running a process and keeping its record. When pl-shexec's turn came, its `--pftelDB` flag was the question: keep pflog as a dependency, with pftel, pfstate and pfmisc behind it, or drop the flag. The discussion that settled it is recorded here because it is the design.

The argument for dropping telemetry altogether was that collection is a solved problem, and solved better than a lab rebuilds it: Loki, Elastic, OpenTelemetry collectors on OpenShift already hold every line a plugin prints. The argument against was that those collectors know pods, not steps; the structure that makes a month of runs answerable, which plugin on which subject took how long and whether it worked, exists only inside the program, and the volume of unstructured lines a platform collects is itself the obstacle to finding it. Both were right about different halves, and the resolution was to separate the record from the transport. The program emits a structured record where its output already goes; the platform carries it as it carries everything else; a reader on the lab's own machine, or a feeder into pfmongo, is written beside the programs and never inside them.

With that settled, the question was where the record should live. hostlib already carried `startedAt`, `endedAt`, `duration`, `status`, `errors` and `host` for every process it ran, and the first proposal was to add the function-timing decorator there. The case against was scope: hostlib's job is that the host runs a command, and a decorator around a Python function is application instrumentation, which is what pflog had always been for, name included; putting it in hostlib would start the growth that had already been refused when the library's name was chosen. pflog 2.0 was therefore a rebuild of pflog, depending on hostlib for the host facts and the timestamp format and re-exporting hostlib's records so that a program imports from one place. The sandwich rule of the stack, that each layer re-exports the models of the layer below, held.

The decorator kept pflog 1.x's shape and changed its substance. The timestamps come from hostlib rather than pftag, the duration from a monotonic clock, the host from hostlib's facts. The outcome is read from the call as a shell reads a program, so a `main` that returns 2 or raises `SystemExit(2)` is a failed span, which is the flag 1.x never had. The span is written on every exit from the call, the exception included, and then the exception goes on. The default destination is one line of JSON on standard error, where a ChRIS plugin's output is already kept by CUBE and read by any collector. `pflog read` is the reader, and `pflog demo` shows a span without code. The `Pflog` class, `pfprint`, the pftel URL grammar, the `--pftelDB` flag, and every dependency but hostlib are gone. pl-shexec 2.0 is the first program on the new library, with `@timed("shexec")` inside `@chris_plugin` where `tel_logTime` had been.
